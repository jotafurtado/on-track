---
name: ot-spec
description: Draft unified spec.md (Outcome plus Phases) and tasks.md with parallelism groups for a track that has intent.md. Chains to implement on user continuation. Intent status may be draft.
---

1. Read `on-track/tracks/NNN-slug/intent.md` in the target repo. Intent status may stay `draft`. Classify each unanswered item under `Open questions`:
   - **Blocking questions**: an answer changes scope, security, data persistence, external integration, architecture, or acceptance. Resolve every one before the summary: ask in rounds of at most four, through the host's question tool when it exists, each question naming the decision it unlocks and offering options with your recommendation first. When the user answers "you decide", decide, record the decision in `spec.md` under `Constraints`, marked `(delegated)`, and list it in the summary for veto. Withhold the summary and do not offer `. para implementar` while any blocking question remains unanswered.
   - **Deferrable questions**: questions whose answers do not block overall architecture or scope. Turn each deferrable question into a bounded task whose Validate names the expected answer or artifact, placed in a group that dependent groups list in `(depends: ...)`.
   Without delegation, do not invent answers to either kind. In Off Road, on from the moment the user asks for it until this spec is approved, a round also carries the design choices you would otherwise settle alone, within the same cap. Approval ends Off Road; a spec returned to `draft` afterwards does not turn it back on unless the user asks again. Off Road adds no field to any artifact and does not carry across sessions: a new session starts with it off until the user asks again, even when a handoff quotes the earlier request.
2. Write `on-track/tracks/NNN-slug/spec.md` from `./assets/spec.md` bundled in this skill. Every constraint in the intent is binding, regardless of provenance. Outcome plus numbered Phases, Out of scope repeated from the intent without widening. Each phase separates the delivered state from its check: `Done:` names the delivered, observable state an observer can see when the phase closes, and `Accept:` names the check that proves it, a command with its expected result or an observable procedure with its expected observation. `Files:` is the explicit list of touched files. Auxiliary outputs go under `assets/`, never loose at the track root.
3. Write `tasks.md` from `./assets/tasks.md` bundled in this skill: organize tasks into named parallel groups using `## Group <name>` headers, with `(depends: <group>)` on the header when a group depends on another. Tasks within one group touch disjoint files and have no data dependency, so they may run concurrently. When unsure about independence, use separate sequential groups. Each task line carries a `(Phase N)` tag naming the spec phase it serves, `Files:` for the files it touches, and `Validate:` naming a command with its expected result or an observable procedure with its expected observation. Include a task for each deferrable open question. When the user makes a qualifying decision, file `on-track/decisions/<NNN-slug>.md` from `./assets/decisions.md` without a separate request and cite supporting refs, research, assessments, source URLs, or repository paths when available. Status is `accepted | superseded` only. Record evidence only in the `## Evidence` body section; the ADR frontmatter has no `evidence` field. A decision qualifies only when BOTH hold: (1) it was a real choice, with at least one alternative weighed and rejected for a stated reason; (2) getting it wrong is expensive: reversing it takes more than reverting a diff (data migration, coordinated change in consumers, external commitment), or a future reader would likely undo it without the recorded reason. Durability alone, a restated user preference or instruction, and local, easily reversible, or obvious choices do not qualify. A user preference with no weighed alternative is a constraint in the intent, not an ADR. To replace an ADR: create the replacement as the next numbered `accepted` ADR, set the original's `status: superseded` and add `superseded_by: <replacement-id>`, and leave the original's decision text and other content unchanged. File outputs point under `assets/`.
4. Regenerate `on-track/INDEX.md` with `../ot-init/scripts/on-track-index.sh <target>` using the owner copy and report any validation error instead of presenting the summary as complete.
5. Run `./scripts/on-track-gate.sh --mode structure --track NNN-slug --root <target>` from this skill as an internal smoke test. Fix any gate failure before presenting the draft; structure mode ignores approval status and task checkboxes.
6. Present a post-phase summary. Format:
   - Four short bullets: outcome, phases, task count, parallel groups.
   - Track location: `on-track/tracks/NNN-slug/`.
   - Next-step line: `. para implementar`.
   Before the track location and next-step line, list delegated decisions so the user can veto them, only when there are any.
   Do not report draft status as failure. Do not present an approval gate.
7. Stop for the user's signal, read as plain text.
   - **Green** (`.`, or a message that only means proceed, such as `go`, `yes`, `continue`, `sim`, `verde`): set frontmatter `status: approved` in both `spec.md` and `tasks.md`. Complete this approval-only action before invoking the `ot-implement` skill for the same track or issuing any product edit. A multi-file action may approve both artifacts together, but must not mix approval with product edits. Approval covers exactly the presented `spec.md` and `tasks.md` content. After approval, any material change to either file (scope, Files, Accept criteria, tasks, or group dependencies) returns both files to `status: draft` and requires a new summary before implementation may continue. Checkbox updates and administrative writes defined by the implement workflow do not count as material changes.
   - **Red** (`x`, or a message that only means stop, such as `stop`, `red`, `pare`, `vermelho`): stop. Leave `spec.md` and `tasks.md` in `draft` and delete nothing; the track resumes when the user asks for this stage again.
   - **Yellow** (any other message, an ambiguous one included): revise the spec or tasks as instructed, regenerate `INDEX.md`, re-run the structure gate, and present the summary again.

Path resolution: `./` paths and `../ot-*` sibling paths resolve from this skill's installed directory, and `on-track/` paths resolve from the target repository root.

Bundled scripts are local Bash with no network calls: the owner index script reads frontmatter under `on-track/` and writes only `on-track/INDEX.md`, or exits with validation errors and leaves it unchanged; the gate script is read-only and only reports track failures.
